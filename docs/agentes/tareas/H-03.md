## Por qué

`maxPendingLogins` (16) cuenta todos los logins en vuelo y el límite de fallos es por cuenta
(`_loginsInFlightPerAccount`, `IsAccountRateLimited`, `ReleaseLoginInFlight` en
`server/Avelora.Server/Net/NetworkServer.cs`). Una cuenta inexistente también calcula un PBKDF2 ficticio
(`SqlitePlayerRepository.Login`). Con un nombre de cuenta distinto en cada saludo y 4 conexiones por IP reconectando,
una o dos IP llenan la cola, saturan el hilo `avelora-login` y los demás reciben `RateLimited`.
`docs/avelora-plan-servidor.md:224` ya preveía el límite por IP.

## 1. La IP de una conexión (`shared/Avelora.Net`)

`NetworkServer` hoy no conoce la IP; solo el transporte (`LiteNetLibServerTransport.CountPeersFrom` usa
`NetPeer.Address` para `maxConnectionsPerIp`). Reutiliza eso:

- `TransportContracts.cs`, interfaz `IServerTransport`: añade
  ```csharp
  /// <summary>Dirección IP remota de una conexión abierta, o cadena vacía si no existe.</summary>
  string GetRemoteAddress(int connectionId);
  ```
- `LiteNetLibServerTransport.cs`: impleméntalo con `_peers.TryGetValue(connectionId, out NetPeer peer) ?
  peer.Address.ToString() : string.Empty`.
- Las tres `FakeServerTransport` de las pruebas (`tests/Avelora.Tests/LoginHardeningTests.cs` ~1067,
  `NetworkServerTests.cs` ~3328, `PersistenceTests.cs` ~2276) lo implementan devolviendo **una IP distinta por
  conexión** por defecto, para que ninguna prueba existente choque con el tope nuevo:
  ```csharp
  public Dictionary<int, string> Addresses { get; } = new Dictionary<int, string>();
  public string GetRemoteAddress(int connectionId) =>
      Addresses.TryGetValue(connectionId, out string? address) ? address : "10.0.0." + connectionId;
  ```
  (`Addresses` solo hace falta en `LoginHardeningTests`; en las otras dos basta la expresión por defecto.)

## 3. Servidor (`server/Avelora.Server/Net/NetworkServer.cs`)

Mismo patrón que el contador por cuenta. Todo en el hilo de red.

- Campos nuevos junto a `_loginsInFlightPerAccount` (~94), con comentario de una línea:
  ```csharp
  private readonly Dictionary<string, int> _loginsInFlightPerIp = new Dictionary<string, int>();
  private readonly Dictionary<long, string> _loginAddressByGeneration = new Dictionary<long, string>();
  ```
  La clave del segundo es la generación de conexión (`_nextConnectionGeneration` es único en todo el proceso), así que
  no hace falta tocar `LoginRequest` ni `LoginResult`.
- `HandleHello` (~783), justo **después** del tope global (`if (_login!.InFlight >= _config.MaxPendingLogins)`, ~875)
  y **antes** de `_pendingLogins[connectionId] = hello;`:
  ```csharp
  string address = _transport.GetRemoteAddress(connectionId);
  _loginsInFlightPerIp.TryGetValue(address, out int ipInFlight);
  if (ipInFlight >= _config.MaxPendingLoginsPerIp)
  {
      Interlocked.Increment(ref _rateLimited);
      RejectHandshake(connectionId, RejectReason.RateLimited);
      return;
  }
  ```
  Y junto al incremento por cuenta (~887):
  `_loginsInFlightPerIp[address] = ipInFlight + 1; _loginAddressByGeneration[connectionGeneration] = address;`
- `DrainLogins` (~917), justo tras `ReleaseLoginInFlight(result.AccountName);`, llama a un método nuevo
  `ReleaseIpLoginInFlight(result.ConnectionGeneration)` escrito junto a `ReleaseLoginInFlight` (~1302): si
  `_loginAddressByGeneration.Remove(generation, out string? address)` es falso, no hace nada; si no, descuenta en
  `_loginsInFlightPerIp` y quita la entrada al llegar a cero (igual que `ReleaseLoginInFlight`).
- **No** toques el manejador de desconexión (~495-505): desconectar no libera el hueco, igual que el global.

## 4. Pruebas xUnit

En `tests/Avelora.Tests/LoginHardeningTests.cs`, usando `Harness`, `BlockingRepository`, `Connect`, `Handshake`,
`HasReject` y `Pump` como `Desconectar_No_Libera_El_Tope_De_Logins_En_Vuelo` (~225). Fija la IP con
`harness.Transport.Addresses[id] = "...";` antes de `Connect`.

1. `Una_IP_No_Pasa_Del_Tope_De_Logins_En_Vuelo_Aunque_Cambie_De_Cuenta`: `MaxPendingLoginsPerIp = 2`; conexiones 1, 2
   y 3 desde `"10.1.1.1"` con cuentas `"a1"`, `"a2"`, `"a3"`; `PollOnce`. La 3 recibe `Reject(RateLimited)` y
   `Assert.DoesNotContain("a3", repository.Accounts)`.
2. `Otra_IP_Entra_Con_La_Primera_En_El_Tope`: igual que la 1 hasta llenar `"10.1.1.1"` con 2; la conexión 3 desde
   `"10.2.2.2"` **no** recibe reject (`Assert.False(harness.HasReject(3, out _))`) y, tras `repository.Gate.Set()` y
   esperar, su cuenta está en `repository.Accounts`.
3. `El_Hueco_Por_IP_Se_Libera_Al_Recoger_El_Resultado`: `MaxPendingLoginsPerIp = 1`; conexión 1 desde `"10.1.1.1"`
   saluda; se desconecta (`RaiseDisconnected(1)`); la 2 desde la misma IP recibe `RateLimited` (desconectar no
   libera). `repository.Gate.Set()`, esperar a que acabe y `Pump`; la 3 desde la misma IP ya entra sin reject.

En `tests/Avelora.Tests/ServerConfigTests.cs`:
4. En la prueba de valores por defecto (~54): `Assert.Equal(2, config.MaxPendingLoginsPerIp);`.
5. En la de ida y vuelta JSON (~182 y ~220): añade `MaxPendingLoginsPerIp = 3` y su `Assert.Equal`.
6. Validación: `MaxPendingLoginsPerIp = 0` y `MaxPendingLoginsPerIp = MaxPendingLogins + 1` lanzan
   `InvalidOperationException`; `= MaxPendingLogins` no.

Si alguna prueba existente con transporte real (`NetworkIntegrationTests`, todas desde 127.0.0.1) falla porque tiene
