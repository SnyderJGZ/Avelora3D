## Cómo encaja con lo de hoy (léelo antes)

Hoy `Zone.OnNpcDied` (`Zone.cs` ~593) llama a `ItemSystem.DropLoot` (`ItemSystem.cs` ~144), que tira cada
objeto **al suelo**, y da la experiencia a `npc.KillerPlayerId` (el del golpe final, puesto en
`CombatSystem.Resolve` ~197). Los jugadores recogen con E (`ResolvePickup`, ~187).

Después de esta tarea:
- El botín (mismas tiradas, mismo `npc.LootRolls`) y la experiencia van al **dueño** del PNJ (§1), no al del golpe final.
- Cada objeto entra **directo** en el inventario del dueño. Si no cabe entero, cae al suelo como hoy, pero
  **reservado al dueño 30 s**: nadie más puede recogerlo hasta entonces; después, cualquiera. Caduca como hoy
  (`groundItemSeconds`). La recogida con E no cambia salvo esa regla: sirve para lo que cayó por inventario
  lleno (y para objetos de otros caducados de reserva).
- Sin dueño válido al morir → **no hay botín, ni oro, ni experiencia**.
- `KillerPlayerId` se sigue poniendo como hoy, pero ya no decide nada.

## 1. Dueño del botín («tag»)

**`NpcEntity`** (`server/Avelora.Server/Entities/NpcEntity.cs`, junto a `KillerPlayerId` ~177), tres propiedades
con `{ get; internal set; }`:
- `LootOwnerId` (`int`, inicial `-1`): id de entidad del jugador dueño.
- `LootOwnerLastHitTick` (`long`): último tick en que el dueño le golpeó.
- `LastAttackerPlayerId` (`int`, inicial `-1`): último jugador con golpe aceptado.

**`CombatSettings`** (`Simulation/CombatSettings.cs`): parámetro opcional nuevo **al final**
`long lootTagTimeoutTicks = 200` (10 s a 20 Hz), validado `>= 1` (`ArgumentOutOfRangeException`), propiedad
`LootTagTimeoutTicks`. Las 7 llamadas existentes siguen compilando.

**`CombatSystem.Resolve`** (`Simulation/CombatSystem.cs`), justo después de `target.Health = Math.Max(...)`
(~187) y antes del `if (target.Health == 0)`:

```
target.LastAttackerPlayerId = attacker.Id
si target.LootOwnerId == attacker.Id:
    target.LootOwnerLastHitTick = tick
si no, si target.LootOwnerId <= 0
       || tick - target.LootOwnerLastHitTick >= _settings.LootTagTimeoutTicks
       || !(entities.TryGet(target.LootOwnerId, out e) && e is PlayerEntity):
    si target.LootOwnerId > 0 → LootOwnerChanges++      // cambio de dueño, no la primera marca
    target.LootOwnerId = attacker.Id
    target.LootOwnerLastHitTick = tick
```

(Si el campo de ajustes se llama distinto, usa el que haya.) Contador público `LootOwnerChanges`.
Expuesto en `Zone` como los otros (`_combat?.X ?? 0`) y en `ConsoleReporter` (periódico y resumen): `cambios_dueno`.

**`NpcSystem.Return`** (~586), en la rama de llegada a casa (donde pone `npc.Health = npc.MaxHealth`): pon
`LootOwnerId = -1` y `LastAttackerPlayerId = -1`. Un PNJ que se cura empieza de cero.

**Dueño al morir** — método nuevo privado en `Zone`:

```csharp
private PlayerEntity? ResolveLootOwner(NpcEntity npc)
// 1) npc.LootOwnerId si Entities.TryGet da un PlayerEntity (vivo o muerto: basta con estar en la zona)
// 2) si no, npc.LastAttackerPlayerId con la misma comprobación
// 3) si no, null
```

Nota: los ids de entidad no se reutilizan; si el dueño se desconecta y vuelve, tiene otro id y pierde la marca.
Es aceptable; dilo en el README.

**`server.json`** y `tools/carga/server-carga.json`: `"lootTagSeconds": 10`. `ServerConfig`
(`Configuration/ServerConfig.cs`): `public double LootTagSeconds { get; set; } = 10d;`, validado en el mismo
método que `GroundItemSeconds` (~552): `>= 1` y `<= 120`, ni NaN ni infinito, mensaje
`"lootTagSeconds debe estar entre 1 y 120."`. `Program.cs` (~247):
`new CombatSettings(config.AttackRangeTolerance, (long)Math.Ceiling(config.LootTagSeconds * SimulationConstants.TickRate))`.

## 3. Reparto (`ItemSystem.DropLoot` y `Zone.OnNpcDied`)

**Shared** (§5) define `LootItemEntry`. En `ItemSystem`: lista de instancia
`private readonly List<LootItemEntry> _lootItems = new List<LootItemEntry>(ProtocolConstants.MaxLootItemsPerMessage);`
y `public IReadOnlyList<LootItemEntry> LastLootItems => _lootItems;`.

Nueva firma (sustituye a la actual): `public int DropLoot(Zone zone, NpcEntity npc, PlayerEntity owner, long tick)`
— devuelve el oro **realmente** sumado.

```
_lootItems.Clear()
type = zone.Npcs?.FindType(npc.TypeId); si null → return 0
gold = 0 (long); inventoryChanged = false
por roll en 0..npc.LootRolls-1:
    si type.GoldMax > 0: gold += _random.Next(type.GoldMin, type.GoldMax + 1)   // solo si hay oro: no cambia la
                                                                                 // secuencia aleatoria de los datos sin oro
    si type.Loot != null, por cada entrada (igual que hoy: chance, luego count = _random.Next(min, max+1)):
        itemType = _catalog.Find(loot.ItemId)
        si itemType != null && CanFit(owner.Inventory, id, count, itemType.MaxStack):
            AddToInventory(...); ItemsLootedDirect++; inventoryChanged = true; AddLootLine(id, count, onGround: false)
        si no:
            si _groundItemCount >= _maxGroundItems → ItemsDiscarded++; continue      // no aparece en el mensaje
            crea el GroundItemEntity como hoy + OwnerPlayerId = owner.Id, ReservedUntilTick = tick + _lootReserveTicks
            ItemsDropped++; ItemsLootedToGround++; AddLootLine(id, count, onGround: true)
oldGold = owner.Gold
owner.Gold = (int)Math.Min(oldGold + gold, PlayerEntity.MaxGold)
si inventoryChanged || owner.Gold != oldGold → zone.NotifyInventoryChanged(owner)
return owner.Gold - oldGold
```

- Objeto que no cabe **entero** → la pila entera al suelo (sin repartir; fuera de alcance).
- `AddLootLine`: si ya hay una línea con el mismo `ItemId` y `OnGround`, suma la cantidad (tope `ushort.MaxValue`);
  si no y hay menos de `MaxLootItemsPerMessage` líneas, añade; si no, `LootLinesTrimmed++` (no debería pasar, ver §4).
- `ItemsDropped` sigue significando «objetos creados en el suelo». Contadores nuevos `ItemsLootedDirect`,
  `ItemsLootedToGround`, `LootLinesTrimmed`, expuestos en `Zone` y `ConsoleReporter`: `botin_directo`,
  `botin_suelo_lleno`, `botin_lineas_recortadas`.

**`Zone.OnNpcDied`** queda así:

```
owner = ResolveLootOwner(npc)
si owner == null → NpcDeathsWithoutOwner++; return
gold = _items?.DropLoot(this, npc, owner, tick) ?? 0
experience = 0
si owner.Level < _levels.MaxLevel:
    experience = CharacterStats.ScaleExperience(npc.ExperienceReward, npc.Level, owner.Level)
    ExperienceGranted += experience; LevelUps += _levels.AddExperience(owner, experience, _classes, _itemCatalog)
GoldGranted += gold
items = _items?.LastLootItems (vacía si no hay _items)
si experience > 0 || gold > 0 || items.Count > 0:
    copia items a un array nuevo y LootGained?.Invoke(owner, new LootGainedMessage((uint)experience, (uint)gold, array))
```

Evento nuevo en `Zone`: `public event Action<PlayerEntity, LootGainedMessage>? LootGained;`. Contadores
`NpcDeathsWithoutOwner` y `GoldGranted` (`long`), en `ConsoleReporter`: `pnj_sin_dueno`, `oro_otorgado`.

## 4. Oro

- **`PlayerEntity`**: `public int Gold { get; set; }` y `public const int MaxGold = ProtocolConstants.MaxGold;`
  (1 000 000 000, definido en shared, §4 abajo; cabe en `int`, `uint` y SQLite; la suma se hace en `long` y nunca desborda).
- **`NpcType`** (`Npcs/NpcCatalog.cs` ~33): `public int GoldMin { get; set; }` y `public int GoldMax { get; set; }`
  (JSON `goldMin`/`goldMax`, defecto 0). Constantes `public const int MaxGoldPerRoll = 10000;` y
  `public const int MaxLootEntries = 16;`. Validación junto al botín (~569):
  - `0 <= goldMin <= goldMax <= 10000`, si no `"npcs.json: <where> tiene goldMin=X, goldMax=Y; debe ser 0 ≤ goldMin ≤ goldMax ≤ 10000."`
  - `loot` con más de 16 entradas → `"npcs.json: <where> tiene N entradas de loot; máximo 16."`
    (así un PNJ da como mucho 16 objetos distintos × 2 destinos = 32 líneas = `MaxLootItemsPerMessage`).
- **Élites:** cada tirada (`lootRolls`) suma su propia tirada de oro: un rango con `lootRolls` 3 da entre
  3·goldMin y 3·goldMax. Máximo por muerte 5 × 10000 = 50 000.
- **Datos:** `server/Avelora.Server/npcs.json` y `tools/carga/npcs-carga.json`: el tipo 2001 `"goldMin": 1, "goldMax": 5`;
  el 2002 `"goldMin": 3, "goldMax": 10`.

**Decisión: el oro viaja en `Inventory`, no en `Progress`.** Justificación (cópiala al README): se ve en la
ventana de inventario; el botín cambia huecos y oro a la vez y ya dispara `Inventory`; y cuando haya tiendas,
comprar/vender cambia los dos en la misma operación, así que un solo mensaje fiable los mantiene coherentes.
`Progress` es nivel, experiencia y vida.

- `InventoryMessage` (`shared/.../Messages.cs` ~767): propiedad `uint Gold`; constructor nuevo
  `(byte slotCount, ushort[] itemIds, ushort[] counts, ushort[] equipment, uint gold)`; el de cuatro parámetros
  llama a este con `0` (el de tres sigue igual).
- `MessageCodec.EncodeInventory`/`TryReadInventory` (~1301/1345): **u32 `gold` al final**. Tamaño
  `1 + 1 + 4·slots + 2·EquipSlotCount + 4` (actualiza las dos fórmulas). Añade
  `ProtocolConstants.MaxGold = 1_000_000_000`; `Encode` lanza `ArgumentException` y `TryRead` devuelve `false`
  si `gold > ProtocolConstants.MaxGold`.
- `NetworkServer.EncodeInventory(PlayerEntity)` (~2022) pasa `(uint)player.Gold`.

## 5. Protocolo v18: `LootGained` (servidor → cliente)

Archivos: `MessageType.cs`, `Messages.cs`, `MessageCodec.cs`, `ProtocolConstants.cs` en `shared/Avelora.Shared/Protocol/`.

- `MessageType.LootGained = 29` (S → C) con su comentario.
- `public readonly struct LootItemEntry` con `ushort ItemId`, `ushort Count`, `bool OnGround` (constructor con los tres).
- `public readonly struct LootGainedMessage` con `uint Experience`, `uint Gold`, `LootItemEntry[] Items`
  (null → `Array.Empty`).
- `ProtocolConstants.MaxLootItemsPerMessage = 32`.
- Formato: tipo (u8) + experiencia (u32) + oro (u32) + N (u8) + N × [itemId (u16), cantidad (u16), banderas (u8;
  bit 0 = cayó al suelo)]. **10 + 5·N bytes**: 10 B sin objetos, 170 B con 32.
- `EncodeLootGained(in LootGainedMessage)`: `ArgumentOutOfRangeException` si N > 32, `Gold > MaxGold`, o algún
  `ItemId == 0` o `Count == 0`. N = 0 es válido (solo experiencia u oro).
- `TryReadLootGained(byte[] buffer, int offset, int length, out LootGainedMessage)`: `false` con tipo distinto,
  N > 32, longitud distinta de `10 + 5·N`, `itemId` 0, cantidad 0, banderas con bits fuera de `1`, u oro > MaxGold.
  Mismo estilo que `TryReadCombatEvent` (`WireReader`, `catch (ProtocolException)`).

**Envío** (`server/Avelora.Server/Net/NetworkServer.cs`): junto a `_zone.ProgressChanged += OnProgressChanged;`
(~229) suscribe `_zone.LootGained += OnLootGained;`. `OnLootGained(PlayerEntity player, LootGainedMessage message)`
copia la guarda de `OnInventoryChanged` (~1759: sesión existe y `session.EntityId == player.Id`), codifica y
`Enqueue(player.ConnectionId, bytes, DeliveryMode.ReliableOrdered, disconnectAfter: false)`. **Solo al dueño.**
Fiable y ordenado: llega después del `Inventory` que ya refleja el botín (`DropLoot` notifica antes del evento).
Contadores `Interlocked` `_lootGainedMessages` y `_lootGainedBytes` → `NetworkStats` (constructor y propiedades)
→ `ConsoleReporter` (periódico y resumen): `botin_msgs`, `botin_bytes`.

## 7. Bots (`tools/Avelora.Bots/BotClient.cs` y `Program.cs`)

Con el botín directo los bots ya no dependen de recoger del suelo: el arma o la armadura entra en el inventario,
llega el `Inventory` y el bot equipa como hoy desde el inventario. **Compruébalo** (busca dónde decide equipar,
~2229/2269); si solo equipara tras recoger, dilo y adáptalo para que mire el inventario.

- **No** cambies `UpdateItemActions` (~2123): la recogida sigue para lo que cae al suelo por inventario lleno.
  Si recoge un objeto reservado a otro, el servidor lo rechaza y se ve en `recogida_rech_reservada`: es esperado.
- Lee `LootGained` junto a `TryReadCombatEvent` (~1435), con `TryReadLootGained`, y suma con `Interlocked`:
  `_lootMessages` (`botin_recibidos`), `_lootExperience` (`botin_exp`), `_lootGold` (`botin_oro`), y la suma
  de cantidades con `OnGround` falso (`botin_objetos`) y verdadero (`botin_al_suelo`). Expónlos como propiedades y
  en el resumen de `Program.cs` junto a `recogidas` (~359 y ~427).
- `TryReadInventory` (~1589): guarda `inventory.Gold` en `_gold` y expón `Gold`; el resumen suma `oro_final`.

## 8. Pruebas (xUnit)

Archivo nuevo `tests/Avelora.Tests/I25Tests.cs`, y amplía `ProtocolTests.cs`, `PersistenceTests.cs`,
`NetworkServerTests.cs`, `ServerConfigTests.cs` y el archivo de pruebas de `NpcCatalog` donde encaje. Copia el
montaje de las pruebas vecinas (catálogo de objetos y PNJ montados a mano; `CombatSettings` con
`lootTagTimeoutTicks` pequeño donde ayude, pero **una** prueba con el valor por defecto 200).

**Dueño:**
1. A golpea primero, B golpea después (dentro de 200 ticks): `LootOwnerId == A`, `LootOwnerChanges == 0`.
2. A golpea en el tick t; B golpea en t+199 → sigue A; B golpea en t+200 → pasa a B, `LootOwnerChanges == 1`.
3. A golpea en t y en t+150; B en t+300 → sigue A (el golpe de A en t+150 renovó la marca).
4. A golpea, se quita A de la zona, B golpea al tick siguiente → B es dueño.
5. PNJ en `Return` que llega a casa → `LootOwnerId == -1`.

**Reparto al morir** (PNJ con botín seguro `chance 1`, oro fijo `goldMin == goldMax`):
6. A es dueño y B da el golpe final: el objeto entra en el inventario de A, la experiencia la gana A, B no
   gana nada, no hay objetos en el suelo, `ItemsLootedDirect` sube.
7. El dueño A ya no está en la zona y B es el último atacante → todo para B.
8. Sin dueño ni último atacante presentes → `NpcDeathsWithoutOwner == 1`, nada en el suelo, nadie gana nada.
9. Élite con `LootRolls == 3` y oro 2..2 → el dueño gana 6 de oro y 3 tiradas de objetos (líneas fusionadas:
   una sola línea con la suma).
10. `Gold` cerca del tope (`MaxGold - 1`) + 5 → queda en `MaxGold` y el `LootGained` dice 1.

**Inventario lleno:**
11. Inventario sin hueco: el objeto cae al suelo con `OwnerPlayerId == A.Id` y `ReservedUntilTick == tick + 600`
    (valor por defecto), `ItemsLootedToGround == 1`, línea con `OnGround`.
12. B intenta recogerlo antes del tick de reserva → `RejectedPickupReserved == 1` y sigue en el suelo; A puede
    recogerlo (libera un hueco antes) dentro de la reserva; en otra prueba B lo recoge en el tick de reserva o después.
13. El objeto reservado caduca como hoy (`groundItemTicks`).

**Datos y configuración:** `goldMin > goldMax`, `goldMax 10001`, `goldMin -1` y 17 entradas de `loot` rechazados
con su mensaje; `lootTagSeconds` 0 y 121 rechazados; `lootReserveSeconds` mayor que `groundItemSeconds` rechazado.

**Protocolo:** `LootGained` ida y vuelta con 0 y con 32 objetos (cantidad 65535, mezcla de `OnGround`), tamaños
10 B y 170 B; `TryRead` rechaza N = 33, un byte de menos y de más, itemId 0, cantidad 0, banderas 2, oro
`MaxGold + 1` y tipo distinto; `Encode` lanza con 33 objetos, itemId 0 y oro `MaxGold + 1`. `Inventory` con
oro 123456 ida y vuelta y su tamaño nuevo; oro `MaxGold + 1` rechazado. `Version == 18`.

**Persistencia:**
- Base v6 hecha a mano (copia cómo las pruebas existentes montan una base vieja, ~línea 626) → al abrir queda en
  v7, la columna `gold` existe y vale 0, y los datos anteriores siguen. Lo mismo desde v5 (comprueba que pasa por 6
  y llega a 7 con la columna).
- Guardar oro 12345 y volver a cargar → 12345. `gold` negativo en la base → 0; mayor que `MaxGold` → `MaxGold`.
- `CharacterSaveService.TryGetLatest` devuelve el oro de la última foto encolada.

**Red** (`NetworkServerTests`, montaje de las pruebas de snapshot/inventario): A (dueño) mata un PNJ con botín y
oro: A recibe un `Inventory` con el oro y **después** un `LootGained` con la experiencia, el oro y el objeto; B,
cerca, no recibe `LootGained`. Al reconectar A, el `Inventory` inicial trae el oro.

**Bots:** `TryReadLootGained` sobre un mensaje codificado suma bien las métricas (si hace falta, extrae el
recuento a un método `internal static` y pruébalo como `BotItemCatalogTests`).
